# 第二十七章：积压任务调度与执行前再验证

> 本章汇总支付服务故障恢复后的调度问题。当前项目的 Worker 只有内存 channel，没有优先级队列、持久化调度或熔断恢复机制；这里是后续扩展的设计笔记。

## 1. 为什么任务不能一视同仁

支付服务熔断器 `open` 时，所有任务都应尊重闸门，不继续轰炸下游。但不同任务的业务处置不同：

| 任务 | 外部副作用是否可能已发生 | 熔断期间的处理 |
|---|---|---|
| 新支付 | 通常尚未发生 | 快速拒绝、延迟接收或排队，并设置背压 |
| 退款对账 | 结果可能已发生但未知 | 保留记录，延迟查询，跟踪业务期限并可升级人工 |
| 已批准补偿 | 可能与已有支付和库存有关 | 保留执行意图，按风险与时限安排恢复 |

新任务可在队列满时返回 `503` 或等效业务响应；已发生副作用的未知任务不能直接丢弃。两者可使用不同队列，例如 `payment-new`、`payment-reconcile`、`payment-compensation`。

## 2. 恢复时慢启动

假设故障期间积压 2000 个对账和 5000 个新支付。下游刚恢复就同时放出所有请求，容易再次触发故障。

```text
open → 停止请求
half-open → 允许少量探测
持续成功 → 逐步提高并发量与速率
失败重新升高 → 再次 open
```

总速率可用令牌桶限制。高风险对账通常优先获得配额，但不能长期占满全部容量，造成普通任务饥饿。可通过保留一部分配额、年龄加权和业务期限共同决定顺序。具体比例需要按支付服务容量与业务要求设置。

## 3. 调度记录

持久化队列至少要知道：

```text
queue_name
priority
risk_level
next_attempt_at
deadline_at
attempt_count
created_at
lease_token
lease_expires_at
```

只挑 `next_attempt_at` 已到且未被其他 Worker 租用的任务。相同风险等级下，可考虑更近的 `deadline_at` 和更早的 `created_at`。真实 SQL 还要处理并发抢占、事务和公平性，不能把简单排序误当成完整队列实现。

## 4. 为什么积压任务执行前要再验证

任务进入队列时有效，不代表等待数小时后仍有效：

```text
用户已取消订单
审批已过期
请求人或审批人权限被撤销
人工已经完成退款
资源被删除或账户被冻结
业务策略发生紧急变化
```

因此 Worker 获得租约后、调用外部服务前，必须重新读取权威数据：

```text
任务与 ToolCall 是否仍处于可执行状态
订单是否取消，目标资源是否仍存在
审批快照和有效期是否匹配
请求人和审批人是否仍有对应权限
此 operation_id 是否已由人工或其他 Worker 完成
当前工具策略是否仍允许执行
```

对于人工已完成退款的情况，首先通过原操作 ID 和外部记录对账，避免再发退款。已失效的任务应按原因转成 `cancelled`、`rejected`、`expired` 或 `manual_review` 等受控状态，保留审计记录；具体状态取决于它是否已经可能产生副作用。

## 5. 重新检查之后仍有竞态

“读取时有效”到“实际调用”之间，订单仍可能被取消。仅先查一次无法提供绝对保证。需要按业务能力补强：

- 用条件更新或事务原子抢占 ToolCall 并验证本地状态。
- 对外调用传稳定幂等键，减少重复效果。
- 外部服务若支持版本号、条件请求或过期时间，也一起传入。
- 对取消和执行同时发生的情况制定确定性的先后与补偿规则。

无法让本地数据库与外部支付 API 自动共享一个事务，所以仍要保留结果未知与对账机制。

## 6. 与 Agent 的边界

模型可以提取金额、订单状态和业务背景，但不能自行提升优先级、绕过熔断、跳过重新授权，或把已取消订单解释为“依然应付款”。队列规则、授权和最终执行条件由后端代码负责。

整个链路可复习为：

```text
持久化操作 → 审批与权限 → 抢占执行权
→ 故障时退避/熔断 → 恢复后按风险调度
→ 执行前再次核验 → 幂等调用
→ 保存确定结果 / 进入对账 / 必要时补偿
```

## 7. 复习自测

1. 为什么服务恢复后不能一次性放出全部任务？
2. 新支付与退款对账为什么需要不同处理？
3. 为什么“已排队”不等于“现在仍获准执行”？
4. 人工已完成退款但队列里还有同一退款任务时，该怎么做？

答案：会冲击刚恢复的下游；新支付还可拒绝，未知退款必须追踪；订单、审批、权限和策略会变化；先按原操作 ID 对账并更新记录，不能再发一笔新退款。
