# 第二十六章：结果未知的对账、重试与熔断

> 本章延续第 23 章的 `outcome_unknown` 和第 25 章的退款场景。当前项目已有模型调用的 `RetryModel`，但没有支付/退款对账器、人工审核队列或熔断器。不要把模型 HTTP 重试与外部写工具重试混为一谈。

## 1. 对账是在查询事实

退款调用超时，可能是请求未到达，也可能是退款已成功而响应丢失。本地应保留：

```text
refund_operation_id = refund:op-pay-123
execution_status = outcome_unknown
```

恢复程序首先用同一个业务操作 ID 向外部服务查询：

```text
查到成功 → succeeded，保存外部 refund_id
查到明确失败 → failed，保存业务错误码
外部仍无法回答 → 保持 outcome_unknown，安排下次对账
```

如果外部服务提供可靠的幂等键，也可用原键重放请求并获得第一次结果。若外部既不支持幂等又不能按业务 ID 查询，高风险动作不能自动重做，只能升级人工核验。

要区分：`retry execution` 是再次请求业务副作用；`retry reconciliation` 是再次查询结果；`manual review` 是停止自动判断、交给人处理。三者的后果不同。

## 2. 不能无限重试，也不能把超时当失败

若支付服务一直超时，继续高频调用会加重故障，且仍无法证明退款失败。对账应同时设置：

```text
max_attempts      最多自动查询次数
max_elapsed_time  从首次未知到现在的最长自动对账时间
deadline_at       业务最迟处理时间
```

任一限制到达，工作流进入 `manual_review`，但退款执行事实仍保持 `outcome_unknown`。例如：

```text
refund_status = outcome_unknown
workflow_status = manual_review
review_reason = reconciliation_exhausted
```

人工队列要展示原支付、退款操作 ID、外部 ID、尝试次数、最近错误、库存状态和建议核查路径；还要有处理时限与升级机制，避免记录长期无人处理。

## 3. 指数退避与抖动

指数退避逐步拉长间隔，并设置上限：

```go
delay := min(baseDelay * (1 << attempt), maxDelay)
```

例如 1、2、4、8 秒增长到最多 5 分钟。多个任务同时故障时，完全相同的间隔会让它们同时重试。加入随机抖动，例如在 `[delay/2, delay]` 内选取下次时间，可以打散尖峰。

外部服务若返回 `429` 和 `Retry-After`，至少等待服务端要求的时间。参数错误、权限拒绝、退款金额越界等明确业务错误不应自动重试。

单任务有界重试仍不足以保护服务：上千个任务各重试八次，仍是大量请求。所以还要有服务级限流和熔断。

## 4. 熔断器的三个状态

```text
closed     正常调用，统计失败率
open       故障率高，暂停向下游发请求
half-open  冷却后只放少量探测请求
```

探测成功后逐步恢复容量；再次失败则返回 `open`。熔断期间不要把每笔退款标成 `failed`，因为外部服务不可用并不能说明各笔退款的业务结果。

可按操作能力区分 `payment.create`、`payment.refund`、`payment.query`。创建接口故障时，查询接口也许仍可对账。若整个服务宕机，还需要服务级总闸门，避免多个细分熔断器一起持续冲击同一故障服务。

## 5. 一个完整例子

```text
10:00 退款请求超时 → outcome_unknown
10:01 第 1 次查询也超时 → next_reconcile_at = 10:01:05
10:01:05 第 2 次查询收到 503 → 后续延迟增加并加抖动
10:03 支付查询接口熔断 open → 不再即时发查询请求
10:08 half-open 允许少量探测
10:09 查询恢复，按原 operation_id 查到 refund-789
10:09 本地记录 succeeded 和 external_id=refund-789
```

若两小时内始终查不到确定结果，则进入人工处理，而非推断“退款失败”。实际时间和次数需按业务时限与支付渠道契约设定，此处只演示流程。

## 6. 复习自测

1. 20 次查询超时能否证明退款失败？
2. 为什么既要指数退避，又要抖动？
3. 熔断器 `open` 时，积压对账任务的执行事实应是什么？
4. 哪些错误不适合自动重试？

答案：不能；退避减少调用压力，抖动避免同步尖峰；保留 `outcome_unknown` 并延迟查询或人工升级；明确的参数、权限和业务规则错误不应盲目重试。
