# 第二十二章：幂等键、结果未知与外部副作用

任务租约可以限制哪个 Worker 有权更新任务，但不能撤销已经发生的外部动作。邮件发送成功后 Worker 崩溃，接管任务的新 Worker 仍可能重复发送。

## 1. 幂等的目标

幂等表示同一个业务操作执行一次或重试多次，最终业务效果相同。

```text
请求可能发送多次
+ 稳定幂等键
+ 服务端去重并重放结果
= 同一业务操作只产生一次效果
```

读取工具通常天然幂等；发送邮件、扣款、创建订单、发布内容等写工具必须重点保护。

## 2. 重放第一次结果

第一次支付成功但响应丢失时，重试不应该只返回“重复请求”，而应该返回第一次支付的成功结果。否则客户端仍然不知道操作是否完成以及对应的外部资源 ID。

```http
Idempotency-Key: task-123:step-2:pay
```

相同键再次到达时，服务端不重复执行，而是返回之前保存的结果。

## 3. 工具执行状态机

```text
pending -> running -> succeeded
                  -> failed
                  -> outcome_unknown
```

- `succeeded`：确认外部操作成功。
- `failed`：确认外部操作没有成功。
- `outcome_unknown`：请求超时或连接中断，无法确定副作用是否已经发生。

超时不能简单等同于失败。若直接把结果未知标成 `failed` 并再次执行，可能造成重复扣款或重复发送。

## 4. 对账与状态校准

处理 `outcome_unknown` 的优先方法是：

1. 使用相同幂等键重新调用外部服务。
2. 使用订单号或操作 ID 查询外部状态。
3. 成功则更新为 `succeeded`，明确失败则更新为 `failed`。
4. 仍无法确定时继续保留 `outcome_unknown`，稍后再次对账或转人工处理。

## 5. 本地执行记录

工具执行表通常需要：

```text
operation_id
idempotency_key
task_id
tool_name
status
output_json
external_id
attempt_count
last_error_code
next_retry_at
owner_token
lease_expires_at
```

`idempotency_key` 应具有唯一约束。并发 Worker 即使同时判断记录不存在，也只有一个能成功插入。

## 6. started 也需要租约

已存在的执行记录处于 `running` 时，可能是另一个 Worker 正在处理，也可能是旧 Worker 已崩溃。因此工具执行本身也需要租约和执行令牌。

租约未过期时返回“处理中”；租约过期后允许新 Worker 接管。完成、失败和续约时必须校验令牌，阻止恢复的旧 Worker 覆盖新结果。

## 7. 幂等键来自业务操作身份

不能简单使用“工具名 + 参数 JSON 哈希”作为幂等键。

两封内容完全相同的邮件可能是用户明确要求的两次合法发送；反过来，同一次业务操作的参数 JSON 可能因为字段顺序或无关默认值变化而产生不同哈希。

幂等键应该回答：

```text
这是不是同一个业务操作？
```

而不是：

```text
这两次请求的内容是否碰巧相同？
```

常见组成是稳定的任务身份、步骤身份和操作类型，例如：

```text
task-123:step-2:send-email
```

如果工作流允许同一步骤合法执行多次，还需要由工作流提前分配不同的 `operation_id`，而不是在每次重试时生成新 UUID。

## 8. 多层保护

```text
Orchestrator
  -> 为业务操作分配稳定 operation_id

本地工具执行层
  -> 唯一约束、状态、租约、结果缓存

外部服务
  -> 接收相同 Idempotency-Key

对账任务
  -> 处理 outcome_unknown
```

模型输出的提示字段不是安全边界。是否需要幂等、能否重试和如何对账，都必须由后端工具层强制执行。

## 9. 本章复习

1. 租约保护任务所有权，但不能撤销外部副作用。
2. 幂等机制应重放第一次结果，而不只是拒绝重复请求。
3. 超时代表结果未知，不代表执行失败。
4. `outcome_unknown` 必须通过相同幂等键、状态查询或人工方式对账。
5. 幂等键来自业务操作身份，不能简单依赖参数内容哈希。
6. 工程目标通常是“请求可以重复，但业务效果只有一次”。
