# 第三十一章：模型上下文、记忆、任务状态与 Go Context

本章继续补基础。开发 Agent 时，“上下文”“记忆”“状态”经常被混着说；在 Go 项目里还会出现 `context.Context`。名字相近，职责却不同。先把它们分开，后面做多轮对话、RAG 和任务恢复才不会把数据放错地方。

## 1. 模型上下文：这一次调用摆在模型面前的材料

假设用户说：“根据昨天的周会记录，告诉我还没解决的风险。”模型这一次可能看到用户问题、必要的历史消息、工具返回的会议片段和输出格式要求。这些被组装进本次请求的信息，就是这里说的**模型上下文**。

模型上下文不是自动无限增长的日记。应用必须决定带入哪些历史、哪些检索片段、哪些工具结果；带得太少会缺信息，带得太多会分散重点、增加成本。OpenAI Docs 说明，多轮对话要通过传递历史，或使用会话/响应的延续机制来管理，而不能假定一次独立模型调用天然知道之前的内容：<https://developers.openai.com/api/docs/guides/conversation-state>。

在本项目的最小循环中，`Orchestrator.Run` 把刚刚得到的工具结果赋给 `observation`，下一次调用 `Model.Decide(goal, observation)` 时传入它。这只是很小的一份运行上下文，不是完整的聊天历史管理系统。

## 2. 记忆：需要时再取出的跨次信息

假设用户一直偏好中文回答。应用可以把这项偏好保存下来，以后构造模型上下文时再取出并加入。这是本课程里说的**记忆**：跨任务或跨会话保留、经过选择后用于未来交互的信息。

记忆不等于把所有聊天原文永久保存，也不等于模型内部永远记得。它涉及写入什么、什么时候取出、是否需要更新或删除、谁能看到等设计。当前 Go 示例没有实现这种长期用户记忆。

## 3. 任务状态：程序需要可靠判断的进度与事实

“任务正在运行吗？”“结果已经保存了吗？”“这笔 `operation_id` 是否执行过？”这些是**应用状态**问题。它们影响程序的下一步动作，不能只靠模型在文字里声称“我记得已经完成”。

本项目的 `task.Repository` 管理 `created → running → completed/failed` 这类任务状态；内存模式的记录会在进程退出后丢失，SQL 模式可以保存数据库中的任务状态。第 28～29 章的 `MemoryExecutionStore` 还在独立原型里追踪工具操作，但尚未接入主流程，也不具备跨重启的支付级保障。

状态记录和外部事实也不是一回事。数据库写着 `running`，外部服务可能已经扣款；状态不确定时要按原操作 ID 查询或对账，而不是让模型猜。

## 4. Go 的 `context.Context`：取消与截止时间的传递通道

Go 代码里的 `ctx context.Context` 是另一种“Context”。它用来沿调用链传递取消信号、截止时间，以及少量请求范围内的值。例如 HTTP 请求被取消，模型或工具调用应尽快停止；Worker 也可以给一次调用设置超时。

它**不是**喂给模型的对话文本，也**不是**长期记忆或任务数据库。不要把大段聊天历史塞进 `context.Context`，也不要指望它在进程重启后恢复任务。

## 5. 把四者放进同一个例子

用户说：“按照我的习惯，用中文总结昨天会议的未解决风险。”

1. 应用从**记忆**中取出“偏好中文”的设置。
2. 应用调用 `search_notes` 获取会议记录，把相关片段和用户问题组装成**模型上下文**。
3. Worker 用 Go 的 **`context.Context`** 控制查询和模型调用的取消与超时。
4. 应用在**任务状态**中记录任务是否运行、是否完成及结果；若有外部写操作，还须单独记录操作身份与执行事实。

一份信息可以从一个位置流向另一个位置：记忆中的偏好可以进入模型上下文，任务状态也可以被摘要后展示给模型。但“展示给模型”不等于“可靠保存”；边界仍要清楚。

## 6. 最短的记法

模型上下文回答“**这次模型看见什么**”；记忆回答“**以后还要记住什么**”；任务状态回答“**系统确认走到哪一步**”；Go `context.Context` 回答“**这条调用链何时取消或超时**”。

OpenAI Docs 也区分最终输出、可延续的历史和可恢复的运行状态；一个 Agent 的运行结果不只是给用户看的最终文字：<https://developers.openai.com/api/docs/guides/agents/results>。
