# 第二十五章：Saga、逆序补偿与不可逆操作

> 本章讨论多个外部步骤组成的可恢复工作流。当前 Go 示例没有订单、支付、物流服务，也没有 Saga 实现；示例是为了理解失败后的处理规则。

## 1. 数据库回滚为什么不够

数据库事务可以回滚尚未提交的 SQL，却无法让已经发送的邮件从收件箱消失，也无法让已经发生的支付“从未发生”。跨服务流程需要新的业务动作处理后果，这叫补偿。

例子：

```text
预订库存 → 扣款 → 创建物流单
成功       成功     失败
```

常见补偿顺序是：

```text
退款 → 释放库存
```

一般沿着已成功步骤的逆序补偿，因为后一步往往依赖前一步。若先释放库存而退款失败，用户已付款却可能失去可履约商品。

逆序是默认推理方式，最终仍要由业务不变量决定。例如“已收款订单必须有对应库存”“同一支付最多一笔退款”“退款后不能继续发货”。支付渠道把“退款受理”与“退款到账”分成不同阶段时，也要规定达到哪个里程碑才释放库存。

## 2. 原操作与补偿操作都要保留

退款不会让原扣款变成失败。审计应记录两条事实：

```text
op-pay-123: charge_payment = succeeded
op-refund-456: refund_payment = succeeded
op-refund-456 compensates op-pay-123
```

补偿本身是新的写操作，执行前必须持久化 ToolCall，使用稳定幂等键、租约、结果未知处理和对账。一个常见键是 `refund:{original_operation_id}`，但仍需符合具体支付服务的幂等协议。

## 3. Saga 的状态

任务汇总状态与单个步骤状态分开：

```text
task = compensating
reserve_inventory = succeeded
charge_payment = succeeded
create_shipment = failed
refund_payment = outcome_unknown
release_inventory = pending
```

汇总状态还可能是 `compensated`、`compensation_failed` 或 `manual_review`。不能只写一个笼统的 `failed`，因为这样无法解释钱和库存分别处于什么状态。

集中式 Saga Orchestrator 明确安排下一步和补偿，适合本项目当前的学习路径。事件驱动的服务协作扩展性更高，但重复消息、顺序和追踪更复杂。模型可以建议计划或解释异常；资金与库存的补偿映射由确定性业务代码规定。

## 4. 退款结果未知时如何处理库存

退款请求超时，状态是 `outcome_unknown`。此时无法判断钱是否已退。多数电商场景下，先继续占用库存，直到支付渠道确认达到预定退款里程碑，能避免“用户仍被扣款，商品却被卖给别人”。

保留库存也有成本，不能无限占用。策略应明确：

```text
保留库存的退款里程碑
最多对账多久
到期后交给谁处理
何时可以人工释放库存
```

具体规则可能随金额、商品稀缺程度、退款渠道能力而异，应由后端策略对象和版本控制决定。模型可总结事实，不临时决定资金与库存的一致性规则。

## 5. 补偿不等于时间倒流

| 原动作 | 可考虑的补偿 | 限制 |
|---|---|---|
| 扣款 | 退款 | 资金流仍保留支付与退款两笔记录 |
| 预订库存 | 释放库存 | 释放前应确认支付和退款条件 |
| 创建物流单 | 取消物流单 | 货物发出后可能无法完整撤回 |
| 发送邮件 | 再发更正邮件 | 第一封仍可能已被阅读 |

不可逆程度越高，执行前越需要清楚的审批、授权和幂等保护。事后发现违规，要单独记录合规事实，并通过新操作补偿，不能覆盖原始执行状态。

## 6. 复习自测

1. 物流单失败时为什么通常先退款、后释放库存？
2. 退款成功后能否把原扣款改为 `failed`？
3. 退款超时、结果未知时能否自动重复发起一笔新退款？
4. 补偿决策为什么由代码和业务策略控制？

答案：先退款有利于保留履约能力，具体仍看业务不变量；原扣款事实仍是成功；应先用原操作 ID 对账或原幂等键查询；补偿涉及真实资金与资源，必须稳定、可测试、可审计。
