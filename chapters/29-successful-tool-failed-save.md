# 第二十九章：工具成功但结果保存失败

第 28 章验证了 `Begin` 失败时不能执行工具。本章看相反的位置：工具已经执行，`Succeed` 却失败。两次故障都表现为调用者拿到错误，但业务含义完全不同。

## 1. 先回答上章问题

设 `charge_card` 已扣款并返回 `payment-789`，随后 `store.Succeed(op-pay-123, result)` 因数据库断线报错。此时不能再扣一次，因为存储错误没有撤销外部扣款。调用者看到的“请求失败”只是本地无法交付确定结果，不是“扣款失败”的证据。

这是一段无法靠本地事务消除的窗口：本地数据库与外部支付服务不是同一个原子提交。若外部支持按稳定 `operation_id` 查询或使用幂等键，恢复时才能安全确认或重放；两者都不支持时，高风险写操作必须停在结果未知，交人工核验。

## 2. 跟着时间线走

```text
T1  Begin(op-pay-123) 成功，本地标记 running
T2  charge_card 扣款成功，返回 payment-789
T3  Succeed 保存 payment-789 失败
T4  用户只看见错误，再次提交同一 op-pay-123
T5  当前内存存储返回 in_progress，不会再次扣款
T6  生产系统中租约到期后应进入 needs_reconcile，先查外部事实
```

注意 T5 只是当前进程内的保护。现有内存存储没有租约，记录会一直停在 `running`；进程一重启，记录又会消失。它既不自动恢复，也不能作为真实支付的安全边界。

## 3. 错误分两层看

```text
调用结果：本次 API/Worker 未能确认完成
业务事实：外部扣款可能已经成功
```

不要把这两层压成一个布尔值 `success=false`。持久化设计至少要保留原 `operation_id`、工具名、冻结参数、执行尝试和可能的外部标识；对账查询应使用同一个业务操作身份，不能新建一笔扣款。

如果 `Succeed` 报错前其实已经提交成功，只是确认响应丢了，再次读取本地记录会得到 `cached`；若确实没提交，则进入结果未知路径。两种情况都不应直接执行第二次 `charge_card`。

## 4. 用故障注入验证边界

`go-api/internal/agent/idempotent_executor_test.go` 新增 `TestIdempotentExecutorDoesNotRepeatWhenSavingResultFails`。测试让工具成功执行，同时让存储的 `Succeed` 强制报错；随后用同一 `operation_id` 重试，断言返回 `ErrOperationInProgress`，底层工具总调用次数仍为 1。

这条测试只证明内存原型在当前进程中的表现；它不能证明跨重启、租约到期或外部支付服务的幂等性。

在 `go-api` 目录运行：

```bash
go test ./internal/agent
```

## 5. 下一步要补什么

接下来应把执行意图和结果放进持久化存储，并明确：何时把过期 `running` 转为待对账，如何用外部原操作 ID 查询，何时允许缓存结果，何时只能人工处理。即使有数据库租约，也不能单靠它阻止过期 Worker 已经发出的外部请求；写工具还需要外部幂等或可靠查询能力。

## 6. 复习自测

1. `Succeed` 报错，能否向用户断言“没有扣款”？
2. 为什么第 28 章内存存储的 `in_progress` 不足以保护真实支付？
3. 对账时为什么必须复用原来的 `operation_id`？

答案：不能，外部扣款可能已成功；内存记录会丢失且没有租约恢复；原 ID 才能关联或去重同一笔业务操作。
