# 第 3 课：Tool Calling

## 一句话理解

Tool Calling 是模型向应用程序提出结构化的工具调用请求。模型负责选择工具和填写参数，应用程序负责校验、授权和真正执行。

## 工具不是模型自带的能力

模型知道“天气查询”这个概念，不代表它能访问实时天气。应用程序需要提供一个工具，例如 `get_weather`，并告诉模型它的用途和参数。

## 完整流程

```text
用户：明天上海天气怎么样？
 -> 模型：请求调用 get_weather(city="上海", date="...")
 -> 后端：检查参数和权限
 -> 后端：调用天气 API
 -> 后端：返回温度和天气结果
 -> 模型：组织自然语言回答
```

模型输出的是“调用建议”，不是执行结果。

## 工具定义的三个部分

1. 名称：简短、唯一、表达动作，例如 `get_weather`。
2. 描述：说明什么时候使用以及不应该什么时候使用。
3. 参数 Schema：规定参数名称、类型、必填项和枚举值。

示例：

```json
{
  "name": "create_task",
  "description": "创建一条待办任务。发送前必须获得用户确认。",
  "parameters": {
    "type": "object",
    "properties": {
      "title": {"type": "string"},
      "priority": {"type": "string", "enum": ["low", "medium", "high"]}
    },
    "required": ["title"]
  }
}
```

## 什么是参数

参数是工具执行所需要的输入。`city`、`date`、`title` 都是参数。Schema 约束的是参数的形状，不保证参数代表的对象真实存在。

例如模型给出 `user_id: "abc"`，后端还要检查这个用户是否存在，以及当前操作者是否有权访问。

## 为什么工具要小而明确

一个工具如果同时负责查询、修改和删除，模型很难稳定选择，权限也难以控制。推荐把能力拆成含义清楚的小工具：

- `search_orders`
- `get_order_detail`
- `cancel_order`

工具的描述也会影响模型选择，因此应该写清楚边界、必填条件和风险。

## 只读和写入工具

只读工具通常风险较低，例如搜索文档、查询订单。写入工具会改变系统或影响其他人，例如发邮件、创建任务、删除数据。

常见策略是：查询可以自动执行；写入先生成预览；发送、删除、付款等动作必须人工确认。

## 后端的安全执行顺序

1. 解析模型给出的工具名称和参数。
2. 使用 Schema 校验类型和必填字段。
3. 根据当前用户重新检查权限。
4. 检查业务规则和目标对象是否存在。
5. 对高风险动作请求确认。
6. 使用幂等键执行，避免重试造成重复写入。
7. 记录调用日志和结果。

## 什么是幂等

幂等表示同一个请求执行一次或多次，最终结果相同。网络超时后，系统可能不知道第一次是否成功；如果没有幂等设计，重试“创建订单”可能创建两笔订单。

## 工具错误如何处理

工具结果应该区分成功和失败，并给出机器可读的错误类型。例如：

```json
{"ok": false, "error": "permission_denied", "message": "无权访问该项目"}
```

模型可以根据错误解释情况或换一个方案，但权限拒绝不能通过反复调用来绕过。

## 本课核心边界

模型可以决定“下一步可能需要查询订单”，但不能决定“绕过权限查询所有订单”。模型可以填写创建任务的标题，但是否真的写入系统必须由后端决定。

## 复习摘要

- Tool Calling 是“模型提议，程序执行”。
- 工具由名称、描述和参数 Schema 组成。
- Schema 保证输入形状，后端业务校验保证安全。
- 写操作需要审批、幂等和审计。
