# 第 2 课：模型 API

## 本课主题

模型 API 是 Agent 的入口：你的后端程序通过网络请求把信息交给模型，再读取模型返回的结果。理解 API 的组成，才能继续学习工具调用和 RAG。

## 1. API 是什么

API 是“程序和程序之间约定好的通信方式”。在这里，你的后端是调用方，模型服务是被调用方。

一次调用通常包含：模型名称、消息列表、生成参数和认证信息。服务返回文本、结构化对象，或者工具调用请求。

## 2. Message 是什么

Message 是一条发送给模型的消息。多条消息组合起来，就形成了本次请求的上下文。

常见角色有：

- `system`：应用设定的规则和身份
- `user`：用户提出的要求
- `assistant`：模型之前的回答
- `tool`：工具执行后的结果

示例：

```json
[
  {"role": "system", "content": "你是一个严谨的会议助理。"},
  {"role": "user", "content": "总结这段会议记录。"}
]
```

## 3. Token 是什么

模型不是按“字数”处理文本，而是把文本切分成 Token。中文、英文、代码的 Token 数量不同。

Token 影响三个方面：

1. 成本：输入和输出越长，通常费用越高。
2. 延迟：需要处理的 Token 越多，响应可能越慢。
3. 上下文限制：模型一次能看到的 Token 数量有上限。

因此不能无限保留聊天记录，需要总结、裁剪或检索相关内容。

## 4. 上下文窗口是什么

上下文窗口是模型单次调用可以读取的最大信息量。它包括输入消息、工具定义、检索文档和模型输出。

上下文窗口不是长期记忆。窗口只影响当前调用；长期记忆需要由应用程序保存，并在合适的时候重新取出。

## 5. 常用生成参数

### Temperature

控制输出的随机性。较低的值通常更稳定，适合数据抽取和工具选择；较高的值更有变化，适合创意写作。它不是“智能程度”参数。

### Max output tokens

限制模型最多生成多少 Token，防止回答无限变长，也有助于控制成本。

### Model

指定使用哪一个模型。模型之间在能力、速度、价格、上下文和工具支持上不同。生产系统应记录模型版本，便于回溯结果。

## 6. 为什么需要结构化输出

自由文本适合展示给人，但后端代码需要稳定的字段。例如意图识别可以要求模型返回：

```json
{
  "intent": "create_task",
  "confidence": 0.94,
  "title": "整理会议纪要"
}
```

结构化输出的好处是：

- 字段名称固定
- 类型可以校验
- 后端容易分支处理
- 结果可以保存到数据库

注意：Schema 只能约束格式，不能保证内容一定正确。后端仍需检查权限、对象是否存在和业务规则。

## 7. API 调用的最小伪代码

```ts
const response = await client.responses.create({
  model: "chosen-model",
  input: [
    { role: "system", content: "你是一个会议助理。" },
    { role: "user", content: userText }
  ],
  text: { format: taskSchema }
});
```

这里的 `client` 是 SDK 客户端，`model` 指定模型，`input` 是消息，`text.format` 指定输出格式。不同厂商 SDK 的字段名称可能不同，但概念基本相同。

## 8. 错误处理

模型 API 可能出现网络超时、限流、认证失败、输入过长或服务端错误。后端需要区分：

- 可以重试的瞬时错误
- 需要减少输入或修改请求的错误
- 不应重试的权限和参数错误

不要把 API 密钥放在前端。浏览器只调用自己的后端，由后端安全地调用模型服务。

## 复习摘要

- API 是后端与模型服务之间的通信协议。
- Message 组成上下文，角色决定消息来源和用途。
- Token 影响成本、速度和上下文容量。
- 结构化输出让模型结果可以被程序可靠处理。
- 格式合法不代表业务正确，后端校验仍然必须存在。
